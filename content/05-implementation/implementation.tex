\chapter{Implementation \label{cha:impl}}

We decided to implement our course in Moodle \ac{lms}. Moodle satisfies the vast majority of our requirements - both functional and nonfunctional. 

It is open source, easy to use with an extensive documentation and community support, and it is possible to deploy on local servers, allowing us to control the amount of computational resources dedicated to it for future scaling. We can restrict access to a set of users defined by us. It stores information about students' progress, generating statistical reports about their behaviors and results automatically. Content can be added easily, with a lot of plugins developed and maintained by community that introduce features not present in basic Moodle itself.

Moodle supports most of the proposed exercise types out of the box - matching exercises, code snippets, drag and drop, multiple choice, and other. Exercises are corrected automatically, feedback can be provided for each answer in an exercise. Tests and feedback forms are also implemented and ready to use in Moodle.

The biggest hindrance is the absence of content types designed for \ac{uml} education. However, we found no other \ac{lms} that would provide this functionality without the need for a workaround, so that is not a decisive issue. For the first version, we decided to substitute the need for an editor with drag and drop exercises.

\subsection{Theoretical content}
We placed the chapter with explanations of concepts of the class diagram right after the introductory assessment quiz and questionnaire. It is implemented as a number of Moodle's book resource\footnote{Moodle, "Book resource", \url{https://docs.moodle.org/501/en/Book_resource}, accessed December 13, 2025.} instances.

The \texttt{book resource} contains a number of pages with static content. It is structured like an actual book with a table of contents, chapters and subchapters. This way the student is aware and in control of the flow of their progress. It can be exported and printed to a .pdf file for future reference by the students as well.

\FloatBarrier

\begin{figure}[ht]
\centering
\includegraphics[height=0.7\textwidth]{assets/images/implementation/new_pics/theory_navigation.png}
\caption{Navigation of the theory section}
\label{fig:theory_nav}
\end{figure}

\FloatBarrier

It begins with an introduction that explains the importance of software modeling and what \ac{uml} is. 

The following sections guide the students through the process of building a class diagram -a simple model of an e-shop- one component at a time, explaining each newly added concept and discussing design choices. 

The first book contains chapters about these concepts: entities, classes, objects, types, methods, attributes, access modifiers. It is followed by a short quiz with exercises related to the topics.

\FloatBarrier

\begin{figure}[ht]
\centering
\includegraphics[height=0.6\textwidth]{assets/images/implementation/new_pics/theory_example.png}
\caption{Gradually building a diagram while discussing modeling challenges as they arise}
\label{fig:theory_example}
\end{figure}

\FloatBarrier

The second book talks about relationships - various types of relationships, differences between them, how they can be added to the example diagram, multiplicity and role names. This book has an associated quiz with a few related exercises as well.

The section continues with a picture of the example diagram and a list of modeling decisions the students might question while reading the theory. Those questions include: \enquote{Should Admin be a separate class?} or \enquote{Why are there no ids, no Product in OrderItem, no getters or setters?}

\FloatBarrier

\begin{figure}[ht]
\centering
\includegraphics[width=0.8\textwidth]{assets/images/implementation/new_pics/discussion_of_design_choices_sample.png}
\caption{Discussion of design details in the example diagram}
\label{fig:theory_discussion}
\end{figure}

\FloatBarrier

The last part of the theoretical section is a short collection of links to more resources about software modeling - a full course, video, article, a link to more examples. There is also a prompt for \ac{genai} in case students want to easily create exercises of their own.

There were other options to implement this section than the book resource, mainly Moodle's Lesson activity\footnote{Moodle, "Lesson activity", \url{https://docs.moodle.org/501/en/Lesson_activity}, accessed October 7, 2025.}, which provides more space for adaptive learning. However, it cannot be referred to in later stages of the course, which is what made us choose the book instead. Appropriate theoretical sections are linked in feedback to exercises in case a student makes a mistake. 

\subsection{Exercises}
Moodle allows us to implement the majority of the exercise types described in earlier chapters (see Section~\ref{exercises_design}). We made 29 exercises in total, most of them focused on simulating modeling diagrams by using Moodle's drag and drop question type\footnote{Moodle, "Drag and drop onto image question type", \url{https://docs.moodle.org/502/en/Drag_and_drop_onto_image_question_type}, accessed December 19, 2025.} and exercises in which the students need to connect diagrams with code. Exercises display hints, reasoning behind correct answers, or links to corresponding theoretical sections after incorrect answers.

All exercise types are: 

\begin{itemize}
    \item Differentiating between relationship types based on description or context
    \item Find mistakes or room for improvement in a diagram
    \item Choosing the right relationship arrow directions
    \item Selecting entities that should be found in a diagram based on a description
    \item Simulating modeling by dragging components onto empty slots in an image of a diagram
    \item Theoretical questions - matching access modifiers to their symbols, differentiating between classes and objects...
\end{itemize}

\subsection{Testing students' knowledge} \label{testing}
Moodle's quiz activity\footnote{Moodle, "Quiz activity", \url{https://docs.moodle.org/501/en/Quiz_activity}, accessed October 7, 2025.} is a selection of exercises from a defined set. It is possible to have static quizes that contain the same exercises every time, or select a number of exercises at random from a set.

We used the quiz activity for all the exercise sections. In the quiz settings, the practice sections show instant feedback for each response in each exercise after the student clicks a check button found under each exercise. They are allowed to retry each exercise multiple times, getting hints in between attempts as well. However, retrying a question multiple times reduces the amount of points received for the question.

In the final assessment and introductory assessment sections, the immediate feedback is not present and number of attempts is lower.

\subsection{Statistical reports} \label{statistics}
Moodle provides statistics regarding individual quizes, exercises and the overall success of individual students\footnote{Moodle, "Statistics", \url{https://docs.moodle.org/501/en/Statistics}, accessed December 13, 2025.}. Reports contain statistics like effective weight or
discrimination index mainly useful for adaptive learning practices. We created our own reports aimed at comparing our 2 courses. 

We used the Configurable reports plugin\footnote{Juan Leyva and Sara Arjona Téllez, "Configurable reports", \url{https://moodle.org/plugins/block_configurable_reports}, accessed February 13, 2026.} to perform queries on the Moodle database. The plugin allowed for convenient .csv exports of the reports. 

Some of the reports were used as dynamically updated statistics for the students - they could view their performance across various categories or compare their performance with other students in the Competitive version of the course. However, most of them were used in the evaluation of the experiments.

\textbf{Blended learning} in our courses is implicit. The courses were used as a part of an actual university class, so the participants experienced both e-learning and traditional learning.

\subsection{Playful course version}

For the playful course version, we implemented several gamification practices: 
\begin{itemize}
    \item Granting rewards for correct answers
    \item Awarding badges for reaching milestones in the course
    \item An informal, playful narration of theoretical and informational sections of the course
\end{itemize}

Native Moodle functions were used to design the rewards and badges. The rewards were inserted into feedback for correct responses in exercises. The badges are awarded for reaching certain milestones in the course and a notification was sent to the user automatically once the award criteria were met.

\subsection{Competitive course version}

In the competitive version of the course, the following elements were introduced:
\begin{itemize}
    \item Leaderboard
    \item Report that displays the student's performance across categories compared to the course's average
    \item Each question displays the average score of all the attempts at it across the entire course
    \item Assertive, strict narration of theoretical and informational sections of the course
\end{itemize}

The leaderboard displays the performance of the 10 best students across both courses. A student would also see their own standing. We used the already mentioned Configurable Reports plugin to create it. 

The same plugin was used to create the comparison report which displays the exercise category, the current user's score in it, the average score in the course, and how the current student compares to the average values.

% AVG IN QUESTIONS

To display the course's average on a given exercise, we used the Generico Filter plugin\footnote{Justin Hunt, "Generico Filter", \url{https://moodle.org/plugins/filter_generico}}. It allows us to run a database query and place its formatted output inside any text on the Moodle site. Since the plugin retrieves data from the database before parsing the arguments it was passed in Moodle content, we opted for a workaround. The query calculates the average score across all exercises along with the number of attempts, and then uses Javascript to retrieve the result for the specific identifier passed as an argument to the filter.

The solution might become problematic in case of very large sites, where retrieving data for all exercises would cause performance issues.

Several changes were made when compared to the intended design (See Chapter~\ref{chapter:design}). Some of the proposed content proved either impractical, hard to implement, or there was not enough room in the courses for the ideas to be included. The changes were:

\begin{itemize}
    \item Course structure change - an additional questionnaire was added at the start of the courses. Originally, it was proposed to only include a questionnaire at the end of the courses
    \item Providing code snippets along with diagram examples in the theory section proved impractical - the diagram example corresponded to a rather large codebase, and including even parts of it would have been either insufficient or overwhelming. We only applied comparison of code and diagrams in exercises
    \item Visual indicators based on the student's current grade. We decided to only include exercise difficulty indicators
    \item Exercises type \textit{Alter a diagram based on instructions} was excluded, as there was no way to implement without creating custom activity types in Moodle
\end{itemize}

\section{Deployment}

We were given access to a server owned by \ac{fiit} for the duration of the experiment (15.3.2026-4.5.2026). The specifics of the server were as follows:

\begin{itemize}
    \item Operating system: Ubuntu 22.04 LTS \footnote{Canonical Ltd., "Ubuntu Server 22.04 LTS (Jammy Jellyfish) Cloud Image", \url{https://cloud-images.ubuntu.com/jammy/current/jammy-server-cloudimg-amd64.img}, accessed March 15, 2026.}
    \item Number of virtual CPU cores: 2
    \item Memory size (GB): 4
    \item Data disk size (GB): 50
\end{itemize}

The amount of computational resources was requested based on the assumption that no more than 80 users would use the site, and it should handle up to 20 users at a single time. The disk size may seem large for the use case, but Moodle stores a lot of user data.
